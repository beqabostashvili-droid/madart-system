# Assumptions

Business/technical decisions that the specification does not define. Each one
is chosen to be safe and easy to change. Numbered for reference from code
comments (`// ASSUMPTION A-07`).

| # | Assumption | Why / how to change |
|---|-----------|---------------------|
| A-01 | **Production duration is per order line, not per unit.** 2 × Khachapuri (30 min) is one task of 30 min. `capacityUnits × quantity` is used for capacity accounting. | Matches the critical scenario (2× Khachapuri starts at 17:30). Change `buildProductionPlan()` in `packages/domain/src/scheduling`. |
| A-02 | **Preparation buffer shifts `plannedReadyAt` earlier:** `plannedReadyAt = targetReadyAt − bufferMinutes`, `plannedStartAt = plannedReadyAt − durationMinutes`. Seed data uses buffer 0 for the demo products so planned times equal the spec examples. | Single formula in the scheduler. |
| A-03 | **ASAP orders** get `targetReadyAt = now + max(duration + buffer)` over production-required items, rounded up to the next whole minute. Items with no production requirement do not affect it. | Function `computeAsapTargetReadyAt()`. |
| A-04 | **Persisted production task statuses** are `SCHEDULED, IN_PRODUCTION, READY, CANCELLED`. `STARTING_SOON`, `START_NOW`, `LATE` are derived: STARTING_SOON when `now ≥ plannedStartAt − startingSoonMinutes` (default 5), START_NOW when `now ≥ plannedStartAt`, LATE when SCHEDULED and `now > plannedStartAt + lateGraceMinutes` (default 2) or IN_PRODUCTION and `now > plannedReadyAt`. | Thresholds are `SystemSetting`s; derivation lives in `deriveProductionDisplayStatus()`. |
| A-05 | **Order state after payment.** `PAID → CONFIRMED → SCHEDULED` happen automatically in the same transaction as payment confirmation. If no item requires production the order goes `CONFIRMED → READY_FOR_ASSEMBLY` immediately. | `OrderEngine.onPaid()`. |
| A-06 | **Order numbers** are `prefix + zero-padded counter`, counter resets daily per branch (`Branch.orderNumberPrefix`, default `A`, padding 3 → `A001`). Sequence lives in `OrderNumberSequence(branchId, dateKey)` and is incremented with a single atomic SQL statement. | Change the padding/reset in `formatOrderNumber()` and `OrderNumberService`. |
| A-07 | **Redis is optional in MVP.** `EventBus` has `InMemoryEventBus` (default) and `RedisEventBus` (when `REDIS_URL` is set). One API instance is assumed unless Redis is configured. | Nest provider factory in `apps/api/src/realtime`. |
| A-08 | **Dev database without Docker.** `pnpm db:local` starts an embedded PostgreSQL 17 (`embedded-postgres`) on port 5433 storing data in `.local/pgdata`. Docker Compose remains the reference setup. | Delete `tools/dev-db` when Docker is standard. |
| A-09 | **Device authentication** uses long-lived device tokens issued from Admin when a device is registered (JWT, `kind: device`). Employees use email + password → short-lived access JWT. POS requires both a device token (which branch/device) and a cashier session. | `apps/api/src/auth`. |
| A-10 | **Mock card payments** succeed unless the order total in tetri ends in `99` (e.g. `12.99 GEL` fails) – deterministic failure path for tests and demos. Mock terminal also emulates a delayed callback. | `MockPaymentTerminalAdapter`. |
| A-11 | **Prices are stored in tetri (integer minor units, GEL).** No floating point money anywhere. | `Money` helpers in domain. |
| A-12 | **Branch-specific price** overrides come from `ProductBranch.priceOverride`; absence means the product's base price. Same for availability per channel: `ProductBranch` flags AND `Product` flags. | `resolveProductForBranch()`. |
| A-13 | **Scheduled (mobile) orders appear on the KDS main board** only when `plannedStartAt − now ≤ boardHorizonMinutes` (default 60); earlier ones are in the *Upcoming* view. | `SystemSetting production.boardHorizonMinutes`. |
| A-14 | **Pickup slots** are 15-minute steps from `now + minLeadMinutes` (default 30) to branch closing time. A slot is unavailable when any station's load in that window exceeds its `CapacityRule.maxCapacityUnits` (default rule: unlimited). | `computePickupSlots()`. |
| A-15 | **Cancellation rules (MVP):** unpaid orders can be cancelled by anyone with `orders.cancel`; paid orders require `orders.refund` and create a refund on the payment; tasks already `IN_PRODUCTION` are marked CANCELLED but the audit log records that production had started. | `OrderEngine.cancel()`. |
| A-16 | **Mock terminal callbacks** are delivered through the same `POST /payments/:id/callback` endpoint a real bank adapter would use, with `providerReference` uniqueness for duplicate suppression. | `PaymentsController`. |
| A-17 | **madart.ge importer** parses the public catalog HTML. If the site structure blocks parsing, the importer falls back to a structured JSON snapshot in `packages/database/seed/madart-catalog.json`; both paths go through the same `CatalogImporter` interface and preview/import flow. | `apps/api/src/catalog-import`. |
| A-18 | **Default language** is `ka`; `en`/`ru` fall back to `ka` when a translation is missing. | `pickTranslation()`. |
| A-19 | **Time zone.** All timestamps are stored in UTC; the branch has `timeZone` (default `Asia/Tbilisi`) used only for daily order-number resets, opening hours and display formatting. | `Branch.timeZone`. |
| A-20 | **Dispatcher "READY FOR CUSTOMER"** is allowed only from `READY_FOR_ASSEMBLY`. A manager with `orders.force_ready` can force it earlier (recorded in audit log). | `DispatchService`. |
| A-21 | **Receipts at kiosk and POS.** Both print through the same `ReceiptPrinterAdapter`. POS prints a receipt after every payment (fiscal when a fiscal printer is configured, otherwise non-fiscal). Kiosk prints a **non-fiscal order slip** (number + QR, and "pay at the cashier" for cash orders) right after the order is placed; whether a kiosk also prints the fiscal receipt depends on the fiscal device installed at that kiosk (Phase 9). MVP renders the slip on screen (`ReceiptPaper`, 80 mm thermal layout) with a Print button that uses the browser/Electron print dialog on 80 mm paper; the mock hardware adapter logs the same document. | `packages/ui/src/receipt.tsx`, `apps/kiosk/src/receipt.ts`, `apps/pos/src/receipt.ts` |
| A-22 | **Imported products get a category-based production default** (ხაჭაპური → HOT_KITCHEN 30′, ლობიანი/ცხობა → HOT_KITCHEN 10–15′, ტორტები → CAKE 20′+5′, ნამცხვრები/ეკლერი/შუ → PASTRY 2–3′, ბოქსები → PACKAGING 8′; drinks/accessories need no production). Set once at import; later imports never touch it. | `CATEGORY_PRODUCTION_DEFAULTS` in `catalog-import.module.ts` |
| A-23 | **Promotions (kiosk/mobile news & ad banner)** — not in the original spec, added for in-store advertising and announcements. A `Promotion` belongs to one branch or, when `branchId` is null, every branch. It is "live" when `active` is true and the current time is within `[startsAt, endsAt)` (both optional/open-ended). Every live promotion (any `kind`) rotates on the kiosk idle/welcome screen (7 s per slide). A `kind` of `NEW_PRODUCT` or `DISCOUNT` *additionally* gets its own spotlight card on the catalog/menu screen — the two are rendered as separate cards side by side so a discount is never buried under news, per explicit request; `kind: GENERAL` (default) shows only on the welcome screen. `badgeText` is a short optional label (e.g. `-15%`, `ახალი`) shown as a pill on the spotlight card, falling back to a kind-specific default. Tapping a spotlight card whose `linkProductId` matches a product opens that product's detail modal directly. Managed from Admin → Promotions with permissions `catalog.read`/`catalog.write` (no dedicated permission was added). | `packages/database` `Promotion` model, `apps/api/src/promotions`, `packages/ui/src/promo.tsx` (`PromoCarousel`, `PromoSpotlight`), `apps/kiosk/src/screens/CatalogScreen.tsx`, `apps/admin/app/pages/catalog.tsx` (`PromotionsPage`). |
